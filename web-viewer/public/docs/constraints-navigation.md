## 2.4 导航与流转约束

导航与流转约束跨越多个界面，规范用户在信息空间中的移动、定位、回溯与恢复。已有约束（P-020 工作记忆、P-021 识别优于回忆、P-022 空间记忆、C-001 预测加工、L-001 层级 - 视觉同构）为导航提供了认知基础，但未被推导为导航场景的具体硬边界。本节将这些基础约束推导为跨界面流转的硬边界，并补充寻路、信息觅食、无障碍导航等已有约束未覆盖的维度。

**本节约束的硬度判定纪律**：钻石仅用于碳基认知 / 生理的不可变边界（工作记忆容量、识别 - 回忆不对称、寻路刚需）；钢铁仅用于硅基物理边界（渲染管线、显示面板、能耗定律）——**平台 API 不属钢铁，走 constraints.md §2.6 平台行为快照（带版本锚点，年度复审）**（依 ADR-0000 §2.4、ADR-0002 §2.1.1）；陶土用于工程约定与行业惯例，必须明确标注 `[ENG]` 并说明理由。**禁止将行业惯例（如 "最多 5 个 tab"）包装成生理必然。**

### 2.4.1 导航层级与广度

| --------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **N-001** | 扁平层级优先于深层嵌套。在总项目数固定时，宽而浅的结构在搜索时间和错误率上优于窄而深的结构；层级深度每增加一级，用户需维持的路径上下文增加一份工作记忆负载。两级结构在搜索速度与迷失感上优于三级结构。 | \[PHYS] 钻石（认知负载）+ \[ENG] 陶土（实验比值）            | 总项目数固定时的比较；分类质量极优时深度的惩罚可缓解（Larson & Czerwinski, 1998）。"两级优于三级" 为 Encarta 百科实验结果（Larson & Czerwinski, CHI 1998），非普适硬阈值。                                                                                                                          | 信息架构设计优先压缩深度而非广度；当内容需要三级以上层级时，必须提供并行检索路径（搜索 / 索引 / 站点地图）；禁止为了 "视觉简洁" 而将平级内容拆入深层级。             |
| **N-002** | 单级可见选项数受分类质量与平台形态共同约束。随机排序列表的单级选项应控制在 4–8 项（\[ENG] 实验值）；分类良好（语义分组清晰）的列表可承载更多项；顶级可见导航项建议 ≤5（\[ENG] 工程约定，非生理硬上限）。        | \[ENG] 陶土（4–8 项随机列表实验值 + ≤5 工程约定；P-020 锚定已摘除） | 4–8 项为随机列表实验值（Paap & Roske-Hofstrand, Human Factors 1986），是实验观测而非工作记忆硬上限；≤5 为顶级导航工程约定（行业惯例，与 iOS UITabBarController ≥6 → More 溢出、Material 3 底部导航 3–5 一致，但均非生理边界）。分类良好时单级可超出此范围（Paap & Roske-Hofstrand 报告组织良好的菜单可多达 64 项而不显著降低绩效）。 | 顶级导航（Tab Bar / 底部导航）≤5 项；超出时必须改用抽屉 / 搜索 / 分组，不得静默溢出为 "更多"；列表项必须语义分组，分组标题可见；随机排列的选项列表不得超过 8 项。 |

### 2.4.2 位置感与寻路



| 约束 ID     | 约束陈述                                                                                                                        | 硬度                 | 边界声明                                                                                                                                             | 对设计的必然要求                                                                                         |
| --------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **N-003** | 界面必须持续提供 "我在哪" 的位置线索。用户在信息空间中建立心理地图依赖三类线索：当前位置标识、路径上下文、可去方向；缺失任一类均增加迷失风险。寻路是三个并行认知过程 —— 理解自己在哪、决定去哪、沿路径执行 —— 任一环节失败即导致寻路失败。 | \[PHYS] 钻石（寻路认知刚需） | Lynch (1960)《The Image of the City》五要素（路径、边界、区域、节点、地标）；Passini (1984, 1992) 寻路三过程；WCAG 2.4.8 Location（AAA，参考级）要求提供用户位置信息。均为质性 / 理论框架，未给出量化阈值。      | 每个界面必须有标题 / 位置标识；导航栏标题、选中态高亮、面包屑至少提供一种位置指示；深层级页面必须显示层级上下文（如 "设置 > 账户 > 隐私"）；禁止无标题的界面。            |
| **N-004** | 层级主干结构优于无约束网络结构。非线性链接网络比层级结构更易导致用户迷失；用户无法有效管理被给予的过度自由度。超文本的两大核心问题是迷失（disorientation）与认知负荷（cognitive overhead）。              | \[PHYS] 钻石（迷失认知负载） | McDonald & Stevenson (1996, Applied Ergonomics) 实验：非线性文本比层级文本更易导致迷失；Conklin (1987, IEEE Computer) 首次系统阐述超文本迷失问题。均为实证 / 理论共识，未给出 "多少链接算过多" 的量化阈值。 | 信息架构以层级树为主干；交叉引用（相关链接、标签）不得破坏层级路径的可回溯性；每个页面必须有且仅有一个规范层级父节点；纯网络结构（如 wiki）必须额外提供寻路辅助（面包屑、分类导航、搜索）。 |

### 2.4.3 回溯与路径记忆



| 约束 ID     | 约束陈述                                                                                                               | 硬度                                              | 边界声明                                                                                                                                                                                                                                     | 对设计的必然要求                                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **N-005** | 返回操作必须始终可用且行为可预测。返回是用户重获位置感的基础机制；禁用或隐藏返回等于切断用户的回溯路径。返回必须回到上一级而非跳转首页 —— 导航栈是后进先出（LIFO）结构，这是平台级行为预期。                 | \[PHYS] 钻石（公理二 因果不虚）+ \[ENG] 陶土（平台手势）           | iOS UINavigationController 管理导航栈，`interactivePopGestureRecognizer` 提供边缘滑动返回（iOS 17+ 另有内容区横向平移返回）；Apple HIG 要求使用标准 Back 按钮（chevron 符号，不带 "Back" 文字）。WCAG 2.5.7 (AA) 要求拖动手势必须有非拖拽替代 —— 返回按钮即边缘手势的替代。根页面无返回是合理的。                            | 每个非根界面必须有显式返回入口；平台原生返回手势不得无故禁用（如需禁用必须有充分理由并提供替代）；返回必须回到上一级界面，不得跳转首页或其他不相关页面；模态 / 任务流的 "取消" 与层级导航的 "返回" 需在视觉上区分。 |
| **N-006** | 面包屑显示层级路径而非浏览历史。面包屑的认知价值在于外化层级位置，免除用户从记忆中重构路径的回忆负担；它必须反映站点层级结构，而非用户的点击序列。面包屑是全局导航的辅助而非替代。                          | \[PHYS] 钻石（P-021 识别优于回忆）+ \[ENG] 陶土（Web / 桌面约定） | NN/g (Laubheimer, 2018) 11 条面包屑设计指南：显示层级结构而非会话历史、当前页不链接、祖先节点为链接、不替代全局导航。WCAG 2.4.8 Location（AAA，参考级）充分技术包括面包屑 trail (G65)。**移动端（iOS/Android）原生不提供面包屑组件**——iOS 用导航栈 + 返回按钮承担 wayfinding，Material 3 官方组件库无 breadcrumbs。面包屑适用于 Web / 桌面深层级场景。 | 面包屑中当前页不可点击；每个祖先节点为链接；分隔符一致（推荐 ">"）；面包屑不得替代全局导航栏；移动端不强制使用面包屑，由导航栏标题 + 返回栈承担位置指示；Web / 桌面应用层级深度 ≥3 时建议提供面包屑。     |
| **N-007** | 中断后恢复导航存在认知惩罚，需外部线索。任务中断后用户重新激活主目标的时间约为正常动作间隔的 2 倍；页面上的路径 / 上下文可视线索可缩短恢复滞后。用户不把界面位置存入工作记忆，而是依赖外部世界作为外置记忆（世界即外部记忆）。 | \[PHYS] 钻石（目标记忆衰减 + 外部记忆）                       | Altmann & Trafton (2002, Cognitive Science) 目标记忆模型：恢复滞后均值 3.8s vs 正常动作间隔 1.9s（约 2×）；该数字来自资源分配任务实验，迁移至导航场景为推论。约 6–8 秒中断前准备窗口可让外部线索有效编码（同研究）。O'Regan (1992) 世界即外部记忆理论。                                                                     | 离开后返回的页面应保留滚动位置 / 选中态 / 输入内容；长流程应提供进度指示（如 "步骤 2/4"）；中断超过数分钟的场景应提供 "继续上次" 入口；禁止在用户返回时重置导航状态到首页，除非用户明确选择 "重新开始"。  |

### 2.4.4 导航形态选择



| 约束 ID     | 约束陈述                                                                                                              | 硬度                                   | 边界声明                                                                                                                                                                                                                                                                                                                                                            | 对设计的必然要求                                                                                                                           |
| --------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **N-008** | 顶级目的地数量与屏幕宽度共同决定导航形态。导航形态不是审美选择，是目的地数量 × 屏宽的函数：少量顶级目的地（3–5）用底部导航 / 标签栏；中大屏可用侧边导航栏；5 个以上顶级目的地需考虑抽屉或分组，但隐藏导航降低可发现性。 | \[ENG] 陶土（工程约定）+ \[PHYS] 钻石（可发现性）    | Material Design 3：底部导航 3–5 目的地（<600dp），Navigation Rail 3–7 项（600–839dp+），抽屉推荐用于 ≥5 个顶级目的地或 ≥2 级导航层级。iOS：UITabBarController 在 ≥6 个控制器时只显示前 4 个 + More（硅基硬行为）；现行 HIG 未写死数字，仅要求 "避免 overflow"。**注意：旧版 HIG "3–5 tabs" 已被现行版软化为定性表述，不得当作 HIG 原文引用。**                                                                                                                 | 顶级导航形态选择必须记录目的地数量与屏宽依据；移动端 3–5 个顶级目的地用底部导航 / Tab Bar；中大屏 3–7 个用侧边导航栏；≥5 个顶级目的地需评估抽屉，但必须配合可见入口；禁止在移动端用汉堡菜单作为唯一主导航（见 N-009）。         |
| **N-009** | 可见导航优先于隐藏导航。隐藏导航（汉堡菜单、抽屉）将可发现性降低近 50%，且增加任务时间与感知难度；可见导航利用识别而非回忆，认知负荷更低。                                           | \[PHYS] 钻石（P-021 识别优于回忆 + 可发现性实证）    | NN/g (Pernice & Budiu, 2016) 179 人量化研究：隐藏主导航使可发现性下降近 50%，任务时间更长，感知难度更高；桌面端损伤大于移动端。Norman (1988) 执行鸿沟 / 评估鸿沟：把知识置于环境中而非要求用户回忆。小屏空间受限时隐藏导航是工程妥协，但必须有补偿机制。                                                                                                                                                                                                         | 核心功能入口必须始终可见；隐藏导航的触发按钮必须有明确标签或图标 + 文字；首次使用时引导用户发现隐藏导航；抽屉打开时必须有遮罩 + 关闭入口；桌面端应优先可见导航（侧边栏 / 顶部导航），不得仅用汉堡菜单。                           |
| **N-010** | 模态用于任务中断而非层级导航。模态将用户带离当前上下文，要求显式操作才能关闭；模态内必须保持单一路径，不得创建 "应用中的应用"。模态体验的核心代价是上下文切换 —— 用户必须暂停主任务，完成模态任务后才能返回。        | \[ENG] 陶土（平台约定）+ \[PHYS] 钻石（上下文切换成本，依 C-001） | Apple HIG (Modality)："Present content modally only when there's a clear benefit"；"Always give people an obvious way to dismiss a modal view"；"Let people dismiss a modal view before presenting another one"；模态内 "providing a single path through the hierarchy"。UIModalPresentationStyle 控制模态样式；UISheetPresentationController 支持 medium（约半屏）/large（全屏）detents。C-001 预测加工：模态是任务流的中断而非延续，用户预期被打破，恢复主任务产生上下文切换成本。 | 模态适用于：需聚焦的短任务、需确认的破坏性操作、内容创建；不适用于：层级导航、长流程、多步骤任务；模态必须有显式关闭入口（按钮 + 手势双保险，见 N-014）；不得在模态上再叠模态（alert 除外）；模态任务完成后必须返回触发它的上下文，不得跳转其他页面。 |

### 2.4.5 状态恢复与深链



| 约束 ID     | 约束陈述                                                                                                                                      | 硬度                                               | 边界声明                                                                                                                                                                                                                                                                                               | 对设计的必然要求                                                                                                                        |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **N-011** | 深链直达必须重建导航上下文。从外部入口（Universal Link/URL Scheme / 通知 / 搜索结果）直达深层页面时，用户缺乏逐级导航的上下文，必须为其重建导航栈或提供清晰的层级出口。孤立的详情页（无返回路径）违反 N-003（位置感）和 N-005（回溯）。 | \[ENG] 陶土（平台机制）+ \[PHYS] 钻石（位置感 N-003）           | iOS Universal Links 通过 `application(_:continue:restorationHandler:)` / `continue(userActivity:)` 接收，可直达深层页面；需配合 UINavigationController 栈重建。URL Schemes 通过 `application(_:open:options:)` 接收，为旧式深链入口。深链落地页的导航栈重建是平台级工程要求。                                                                           | 深链落地页必须有返回 / 上一级入口；深链落地页的导航栏标题必须正确反映层级；无法重建上下文时应落地到相关列表页而非孤立详情页；深链落地页应标注 "从外部链接进入"（如需要），让用户理解上下文缺失的原因。                          |
| **N-012** | 应用冷启动后应恢复用户导航状态。用户期望离开时在哪，回来时还在哪；状态丢失迫使用户重新导航，增加认知负担与挫败感。预测加工（C-001）要求系统行为与用户预期一致 —— 冷启动后落地到首页违反用户 "继续上次" 的预期。                            | \[PHYS] 钻石（C-001 预测加工 + 外部记忆）+ \[ENG] 陶土（平台 API） | iOS State Restoration 为 opt-in：`application(_:shouldSaveApplicationState:)` 与 `application(_:shouldRestoreApplicationState:)` 两个 Bool 开关；`restorationIdentifier` 标记需恢复的视图控制器；`UIUserActivity` / `stateRestorationActivity` 携带活动态。O'Regan (1992) 世界即外部记忆 —— 界面的稳定状态本身就是用户的外置记忆。隐私敏感场景（如银行应用）可选择不恢复。 | 导航栈深度、当前选中 tab、滚动位置应在冷启动后恢复；无法恢复时应落地到合理的默认页并提供 "继续上次" 入口；隐私敏感场景（需重新登录）不恢复是合理的，但必须在登录后提供 "返回上次位置" 的选项；禁止在用户未明确选择 "重新开始" 时重置导航状态。 |

### 2.4.6 出路设计



| 约束 ID     | 约束陈述                                                                                                        | 硬度                                 | 边界声明                                                                                                                                                                                                                                            | 对设计的必然要求                                                                                                                                      |
| --------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **N-013** | 零态 / 错误态 / 加载态必须提供出路。无出路的状态页将用户困在认知死胡同；闭合性（P-014）要求每个状态都必须可见且可退出。情绪时间（C-003）指出不确定性 + 等待 = 焦虑 ²，无出路的加载态放大焦虑。 | \[PHYS] 钻石（P-014 闭合性 + C-003 情绪时间） | 覆盖所有非内容态：空数据（零态）、加载失败、网络错误、无权限、加载中。P-014 要求零态必须自证（否则闭合性无法触发 "还有更多" 预期）；P-007 要求 >1s 无反馈产生焦虑，>10s 无确定性指示产生放弃行为。加载态不得阻断返回操作 —— 用户在等待时应有权退出。                                                                                                       | 零态必须说明 "为什么空" 和 "能做什么"（如 "还没有项目，点击创建"）；错误态必须提供重试 / 返回 / 帮助至少一个出口；加载态超过 1s 必须显示进度或骨架屏（已有 P-007）；加载态不得阻断返回操作；无权限态必须说明如何获取权限或提供返回入口。             |
| **N-014** | 模态 / 覆盖层必须有显式出口。仅靠手势关闭的覆盖层易被意外关闭且对无障碍用户不友好；显式按钮 + 手势是双保险。出口焦虑（exit anxiety）是模态场景的认知刚需 —— 用户必须确信自己能随时退出。     | \[PHYS] 钻石（出口焦虑，依 C-003）+ \[ENG] 陶土（平台约定）  | NN/g (2019, Cancel vs Close；2022, Accidental Dismissal of Overlays)：有清晰 X 按钮的覆盖层被意外关闭的概率更低；即使支持手势关闭，也应提供可见的 X 按钮。Apple HIG (Modality)："Always give people an obvious way to dismiss a modal view"。WCAG 2.5.7 (AA) 要求拖动手势必须有非拖拽替代 —— 关闭按钮即手势的替代。C-003 情绪时间：无法退出的不确定性 × 控制感缺失放大焦虑 —— 出口焦虑的机制依据。 | 所有模态、抽屉、弹出层、底部 sheet 必须有可见的关闭 / 取消按钮；手势关闭可作为补充但不可作为唯一出口；关闭按钮位置必须符合平台惯例（iOS 顶部工具栏，Android 顶部导航栏）；区分 "取消"（放弃变更）与 "关闭"（关闭视图，保留变更）—— 两者语义不同，不得混用。 |

### 2.4.7 破坏性操作与撤销



| 约束 ID     | 约束陈述                                                                                                                                          | 硬度                                             | 边界声明                                                                                                                                                                                                                                   | 对设计的必然要求                                                                                                                                                                                                     |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **N-015** | 优先可逆设计而非依赖确认对话框。频繁的确认对话框会训练用户机械点击 "确定"，反而保护不了真正危险的操作；可逆性让用户敢于探索，且不打断心流。确认对话框的 "确认后" 流程存在三个问题：对话框太常见、多数时点过去也无害强化了 "点 OK" 习惯、用户采取动作时注意力已转向下一任务。 | \[PHYS] 钻石（P-011 运动误差 + 探索行为）+ \[ENG] 陶土（具体实现） | Stiegler & Karp (2011, HP Laboratories 技术报告 HPL-2011-96) 提出确认对话框训练用户机械跳过的假说，**原文自陈 "需要用户研究检验"—— 这是设计提案，不是已验证的实证结论**，证据强度有限。Carroll & Carrithers (1984, CACM) 训练轮研究支持 "减少新手错误路径" 的思路。可逆性促进探索为 Norman (1988) 与 Shneiderman (1983) 的理论主张。 | 删除 / 移动 / 修改等操作应优先提供 undo（撤销 / 回收站 / 草稿自动保存）；确认对话框仅用于不可逆且后果严重的操作（如账户注销、支付确认、不可恢复的删除）；确认对话框必须明确说明后果（如 "将删除 3 个项目，此操作不可撤销"），不得仅用 "确定 / 取消"；undo 入口的持续时间需足够用户感知（\[ENG] 工程约定：≥5s 或直到下一个操作，参考 iOS 系统级撤销横幅时长；P-007 的 1s 仅为感知下限，非时长依据）。 |
| **N-016** | 破坏性操作必须可撤销或有明确的后果预览。运动误差必然存在（P-011），用户可能误触破坏性操作；不可逆操作必须在执行前让用户明确感知后果。因果不虚（公理二）要求每个行为有可感知的反馈 —— 破坏性操作的反馈必须包括后果确认。                              | \[PHYS] 钻石（P-011 运动误差必然 + 公理二 因果不虚）            | 破坏性操作 = 删除、覆盖、发送、支付、注销等不可自动恢复的操作。P-011 指出成人手指有生理震颤（约 8–12Hz，振幅 <1mm），运动误差必然存在。P-009 菲茨定律指出目标越小、距离越远，操作时间越长、误差越大 —— 破坏性操作的热区设计需考虑此点。                                                                                                    | 可撤销操作执行后必须提供 undo 入口（见 N-015）；不可逆操作必须有后果预览（如 "将删除 3 个项目，此操作不可撤销"）；破坏性操作的热区不得与高频操作相邻过近（参考 P-009 菲茨定律，增加距离或增加确认步骤）；破坏性操作的视觉样式必须与普通操作区分（如红色文字 / 图标，参考 C-004 语义色相）。                                              |

### 2.4.8 入口一致性与可预测性



| 约束 ID     | 约束陈述                                                                                                                     | 硬度                                                   | 边界声明                                                                                                                                                                                                                                                                                      | 对设计的必然要求                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **N-017** | 站内导航元素的位置、行为、标签必须一致。站内一致性比跨站惯例一致性更重要 —— 违反外部惯例只产生首次访问的短暂代价，破坏站内一致性才是主要风险。导航元素的稳定位置本身就是用户的外置记忆（世界即外部记忆），移动它等于摧毁用户的外置检索线索。 | \[PHYS] 钻石（C-001 预测加工 + P-022 空间记忆）+ \[ENG] 陶土（具体位置） | McCarthy et al. (2003, UCL 眼动研究，N≈30)：菜单位于左 / 上 / 右三种位置，首次访问时左侧菜单更快（p<.05），但第二次访问时此差异消失 —— 跨站惯例违背只产生一次性代价；复杂站点搜索时间比简单站点多约 50%（F (1,29)=7.33, p<.05）。结论原文："站点内部一致性比与外部惯例的一致性更重要"。WCAG 3.2.3 Consistent Navigation (AA) 要求多页间导航机制的相对顺序保持一致。O'Regan (1992) 外部记忆理论。                           | 同一导航组件在所有页面的位置必须固定；同一功能的图标 / 标签在所有页面必须一致；导航元素不得在页面间无理由地移动位置；如因响应式布局需调整导航位置（如移动端底部导航 → 桌面端侧边栏），必须在断点处明确切换，不得在同一切口内渐变；WCAG 3.2.3 (AA) 要求导航机制的相对顺序在多页间一致。                                |
| **N-018** | 链接 / 菜单项的标签必须与目标内容语义一致（信息气味）。用户根据近端线索（标签文字、图标、摘要）推断远端信息价值；标签与目标不一致产生预测误差，消耗工作记忆。信息气味是用户决定 "继续在当前斑块挖掘还是跳走" 的核心依据。         | \[PHYS] 钻石（信息觅食理论 + C-001 预测加工）                      | Pirolli & Card (1995, CHI; 1999, Psychological Review) 信息觅食理论：信息气味（information scent）= 用户从近端线索推断远端信息价值的过程；信息斑块（information patch）= 信息成簇出现的区域。用户最大化单位成本获取的有价值信息率。Larson & Czerwinski (1998) 发现信息气味质量影响 Web 搜索效率。C-001 预测加工：输入与预测一致时认知负荷极低，不一致时产生预测误差。均为理论框架 + 实验支持，未给出 "标签长度应为 N 字" 的量化阈值。 | 导航标签必须描述目标内容而非动作（如 "设置" 而非 "点这里"）；避免模糊标签（如 "更多"、"其他"、"东西"）—— 模糊标签 = 低信息气味；图标必须有文字标签或可访问名称（P-021 识别优于回忆，图标 + 文字双重编码）；链接文本必须脱离上下文即可判断目的（WCAG 2.4.9 Link Purpose，AAA，参考级）；禁止 "点击这里" 式的链接文本。 |
| **N-019** | 同一功能在不同入口的行为必须一致。用户从不同路径到达同一功能时，预期行为相同；入口不一致产生预测误差，破坏可预测性。同一功能的组件在多页间的视觉识别必须一致。                                          | \[PHYS] 钻石（C-001 预测加工 + L-003 状态互斥）                  | WCAG 3.2.4 Consistent Identification (AA)：相同功能的组件在多页间视觉识别一致。C-001 预测加工：一致性是认知能耗最小化的物理必然。L-003 状态互斥：同一元素在同一时刻只表达一个最高意图 —— 同一功能在不同入口的状态表达必须一致。                                                                                                                                              | 从不同入口（Tab Bar、搜索结果、深链、推送通知）触发同一功能时，结果状态必须一致；如因入口上下文不同需差异行为，必须在界面上明确说明差异原因；同一功能的图标 / 标签 / 位置在所有入口必须一致（WCAG 3.2.4 AA）；禁止 "从 A 入口删除是软删除（可恢复），从 B 入口删除是硬删除（不可恢复）" 式的不一致行为。                |

### 2.4.9 无障碍导航



| 约束 ID     | 约束陈述                                                                                                                  | 硬度                              | 边界声明                                                                                                                                                                                                                                                                                                                              | 对设计的必然要求                                                                                                                                                                                                                               |
| --------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **N-020** | 必须提供绕过重复导航块的机制。键盘用户和屏幕阅读器用户在每个页面都需遍历重复的导航链接，这是不必要的负担；"跳到主内容" 链接是标准解法。重复导航块必须用语义化标签区分，让辅助技术用户知道这是什么导航。                 | \[PHYS] 钻石（生理基础：重复遍历负担）+ \[ENG] 陶土（WCAG 2.4.1 A 条款实现）    | WCAG 2.4.1 Bypass Blocks (A)："A mechanism is available to bypass blocks of content that are repeated on multiple Web pages." 充分技术：G1（添加跳到主内容链接）、H69（为每个重复块提供标题）、ARIA11（使用 landmarks）。WCAG 4.1.2 Name, Role, Value (A)：导航元素的名称、角色、状态可被辅助技术感知。原生应用由平台语义化处理（如 iOS 的 `accessibilityElements`），但仍需确保导航元素的 `accessibilityLabel` 正确。     | 页面顶部必须有 "跳到主内容" 链接（键盘聚焦时可见，非聚焦时可隐藏）；重复导航块必须用语义化标签（如 `<nav aria-label="主导航">`、`<nav aria-label="页脚导航">`）；导航元素的 `accessibilityLabel` 必须描述其目的（如 "返回设置" 而非 "返回"）；原生应用的导航栏必须设置正确的 `accessibilityTraits`（如 `.button`、`.header`）。             |
| **N-021** | 键盘焦点顺序必须保留意义与可操作性。焦点移动顺序必须与视觉阅读顺序和逻辑操作顺序一致；混乱的焦点顺序让键盘用户无法理解界面结构。模态打开时焦点必须 trapped 在模态内，关闭时返回触发元素。焦点不得被 sticky 元素完全遮挡。 | \[PHYS] 钻石（生理基础：运动 / 视觉障碍）+ \[ENG] 陶土（WCAG 2.4.3 A + 2.4.11 AA 条款实现） | WCAG 2.4.3 Focus Order (A)："focusable components receive focus in an order that preserves meaning and operability." | **N-022** | 必须提供多种定位页面的方式。用户有不同的导航偏好和能力；单一导航路径将部分用户排除在外。多种方式也为迷路用户提供逃生舱 —— 当主导航无法满足时，搜索 / 站点地图 / 目录是替代路径。                         | \[PHYS] 钻石（生理基础：能力差异需多路径）+ \[ENG] 陶土（WCAG 2.4.5 AA 条款实现）   | WCAG 2.4.5 Multiple Ways (AA)："More than one way is available to locate a web page within a set of web pages except where the web page is the result of, or a step in, a process." 豁免：流程中的步骤页（如结账流程的第 2 步）可只有一种方式。充分技术：G63（提供站点地图）、G64（提供目录）、G161（提供搜索功能）、Sitemap.xml。Apple HIG 指出搜索有 3 个主要入口位置（Tab Bar / 工具栏 / 内容内联），搜索是导航的并行路径。 | 除主导航外，必须提供至少一种替代定位方式（搜索、站点地图、目录、相关链接）；搜索结果必须可导航到目标页（不得仅展示摘要而无链接）；站点地图 / 目录必须覆盖所有可公开访问的页面；流程中的步骤页（如多步表单）可豁免，但流程入口必须可从主导航到达；搜索入口必须始终可见（不得仅藏在汉堡菜单中，见 N-009）。                                                                              |
| **N-023** | 拖动手势导航必须有非拖拽替代。边缘滑动返回、抽屉拖出、滑动删除、可排序列表等手势对运动障碍用户不可用；必须提供按钮式替代。拖拽替代也是 WCAG 2.2 的新增要求。                                   | \[PHYS] 钻石（生理基础：运动障碍）+ \[ENG] 陶土（WCAG 2.5.7 AA 条款实现）   | WCAG 2.5.7 Dragging Movements (AA, WCAG 2.2 新增)："All functionality that uses a dragging movement for operation can be achieved by a single pointer without dragging, unless dragging is essential." P-010 热区 ≥44px 确保替代按钮的可点击性。P-011 运动误差必然存在 —— 拖拽操作对运动障碍用户尤其困难。iOS 边缘滑动返回已有返回按钮作为替代（符合要求），但自定义拖拽手势需额外提供替代。                      | 抽屉必须有汉堡按钮 + 滑动双入口（不得仅靠滑动打开）；可排序列表必须有上下移动按钮或编辑模式下的拖拽替代；滑动删除必须有编辑模式下的删除按钮（左滑出现删除按钮是常见模式，但必须确保编辑模式也能删除）；自定义拖拽手势（如拖拽卡片排序）必须提供 "编辑模式" 或按钮式替代；所有替代按钮的热区必须 ≥44px（P-010）。                                                                      |
