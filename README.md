# 🌊 Lumtract

**结构如水，逻辑如光。**

在硅基的精确与碳基的感知之间，构建可视化的拓扑叙事。

Lumtract 是一个基于 Monorepo 架构的结构化数据可视化平台。它致力于将复杂的 DAG（有向无环图）数据转化为直观、流畅的交互体验——如水面折射出的光影，既有严谨的骨架，亦有灵动的质感。

它同时是 **Lumtact · 水之波光** 设计体系的可执行载体：每一个设计值都可以被追溯到一条经过验证的目的、一组被诚实的约束、一次清晰的冲突裁决、一个明确的来源标注。

## 两个名字

这套体系里有两层结构，恰好对应水之波光自身的隐喻：

| 名字 | 是什么 | 角色 |
|---|---|---|
| **Lumtract** | **推导器**：把目的推导成设计值的机器（图谱生成 / 约束校验 / 审计） | 工具层——推导出"正确" |
| **Lumtact** | **水之波光设计理念**：公理 → 约束库 → 推导方法 → 实例档案 | 理念层——定义"正确" |

> Lumtract 是 Lumtact 的可执行载体：推导器不产生理念，它让理念成为可验证、可审计的产物。水没有光，是虚空；光没有水，是无处落脚的射线。人（用户与设计者）与之相遇，才有波光。

README 标题写 `Lumtract`（推导器是项目主体），设计资产与推导记录源自 `Lumtact`（水之波光）——这不是改名没改全，是两个不同的东西。但读者会混淆，所以在此明确分层。

## 架构概览

本项目采用 Rust + Next.js 混合架构，遵循"数据驱动视图"原则：

| 层级 | 技术栈 | 职责 |
|---|---|---|
| 数据引擎 | Rust (`dag-generator`) | 扫描 `web-viewer/public/docs/` 下的 Markdown 文档，生成结构化拓扑数据（JSON），输出到 `web-viewer/public/dag-manifest.json` |
| 表现层 | Next.js 16 (`web-viewer`) | 数据驱动的文档阅读器，负责渲染知识图谱与文档内容 |
| 设计系统 | Storybook 10 (`web-viewer/.storybook`) | 独立的 UI 组件实验室，用于开发与调试 |
| 约束校验 | Node + Vitest | 把设计推导法的审计清单变成可执行断言（见[三道关卡](#三道关卡)） |

## 快速开始

### 0. 环境准备

- Rust 1.70+
- Node.js 20+（推荐 LTS 版本）

### 1. 生成知识图谱数据

Lumtract 的核心是文档知识图谱。运行 Rust 引擎扫描 `web-viewer/public/docs/` 下的所有 Markdown 文档，提取链接关系与层级结构：

```bash
cd dag-generator
cargo run --release
```

执行后，终端会显示：

```
✅ Manifest generated: ../web-viewer/public/dag-manifest.json
```

> **注意**：扫描路径基于**当前工作目录**解析——请保持 `cd dag-generator` 状态运行。
> 等价方式：`cd web-viewer && ../dag-generator/target/release/lumtract-dag`（已编译二进制）。
> 从仓库根直接运行二进制会报 `Failed to resolve docs root`。

### 2. 启动前端

```bash
cd web-viewer
npm install
npm run dev
```

访问 http://localhost:3000 查看文档知识图谱。

### 3. 启动组件实验室（Storybook）

```bash
cd web-viewer
npm run storybook
```

访问 http://localhost:6006，侧边栏应出现 **Lumtact** 分组：

```
Lumtact
├── 01 · WaveButton 按钮
├── 02 · BreathInput 输入框
├── 03 · EdgeVeilTable 表格
├── 04 · Ripple 实验台
└── 05 · Tier 降级阶梯
```

> **在仓库根目录也能跑**：根 `package.json` 已配置转发，
> `npm run build` / `npm run storybook` / `npm run verify` / `npm run test` 均可直接使用。

## 文档图谱

Lumtract 本身就是一个知识图谱浏览器。`web-viewer/public/docs/` 目录下的所有 Markdown 文档会被自动扫描、建立链接关系，并在前端以分层导航的方式呈现。

| 文档 | 内容 | 卷 |
|---|---|---|
| `philosophy.md` | 设计推导法 · 公理系统 | 卷一 |
| `constraints.md` | 设计推导法 · 约束库（含 §2.6 平台行为快照） | 卷二 |
| `constraints-navigation.md` | 导航与流转约束 N-001~N-023（卷二的导航分册） | 卷二 |
| `derivation.md` | 设计推导法 · 推导引擎（含推翻路径） | 卷三 |
| `archive.md` | Lumtact 实例档案 | 卷四 |
| `navigation.md` | 导航索引：N-系列汇总 + 组件映射 + 负债 | 索引 |
| `system-summary.md` | 体系总纲 | — |
| `adrs/` | 架构决策记录 ADR-0000~0008（管辖边界 / 修订 / 分级 / 固化 / 推翻路径 / 辉光语义） | 决策记录 |
| `engineering-guide/` | 工程指引（导航基线等，[ENG] 陶土输入材料） | 指引 |
| `research-notes-navigation-constraints.md` | N-系列证据登记与覆盖矩阵 | 证据 |

这些文档可通过 http://localhost:3000 直接阅读，文档内部的 Markdown 链接会在应用内平滑导航，无需刷新页面。

### 四卷关系

```
卷一：哲学（公理系统）
    ↓ 提供第一原理与推导纪律
卷二：约束库（知识库）
    ↓ 提供硬边界与量化阈值
卷三：推导引擎（方法论）
    ↓ 提供从目的到形态的推导协议
卷四：实例档案（应用记录）
    ↑ 验证/质疑/反馈 → 触发卷二/卷三迭代
```

- **知识从上往下流**：哲学 → 约束 → 引擎 → 实例
- **质疑从下往上流**：实例发现问题 → 质疑约束或引擎 → 通过版本迭代修正
- **实例永远不能反向修改公理**
- **修订走 ADR**：约束与流程的每一次语义变更都记录在 `adrs/`（ADR-0000~0008）；版本冻结后不原地修改，旧版保留为历史

## Lumtact 组件资产

设计体系的每一个组件都是一次完整推导的产物，且**推导过程写在代码里**——`tokens.ts` 的每个值带 `source / constraints / why / hardness` 标注，stories 的 docs 块写着版本推翻史。

> 这样做的原因：Agent 读到代码，就读到语义。

### 组件导航

| # | 组件 | 验证的约束 |
|---|---|---|
| 01 | **WaveButton** 按钮 | `P-010` 热区 44px、`P-004` 起始可见性、T0–T3 降级 |
| 02 | **BreathInput** 输入框 | `P-019` 光敏安全、`R-001` 并发上限、`C-003` 情绪时间 |
| 03 | **EdgeVeilTable** 表格 | `P-014` 闭合性、`D-001` 极性、`L-001` 层级单调 |
| 04 | **Ripple 实验台** | 缓动三档定格、容器尺寸、昼夜极性 |
| 05 | **Tier 降级阶梯** | 帧率探针、滞回、实时诊断 |

底层基础件：

| 文件 | 职责 |
|---|---|
| `LumtactRipple.tsx` | 波纹引擎。果从因的位置长出 |
| `useTier.ts` | 降级档位探测（帧率、reduced-motion、pointer） |
| `lumtact-tokens.css` | **令牌单一事实源** |
| `tokens.ts`（`src/design/tokens.ts`） | 令牌类型与默认值——每个值带 `source / constraints / why / hardness` 标注 |
| `contrast.ts` / `css-scan.ts` | 颜色与 CSS 结构化解析工具 |

### IP 规则：果，从因的那个位置长出

> 任何反馈的起点，必须是触发它的那个空间坐标。

这不是一个动效，是一条规则。它能长出无数形态——卡片涟漪、输入框呼吸、边缘遮蔽、加载水纹。**别人抄走任何一个形态，都抄不走这条规则。**

它的三条边界（缺了就会退化成装饰）：

- 起始 **<100ms 必须可见**（`P-004`）—— 尾部才允许缓慢
- 并发有上限（`R-001`），仅聚焦/悬停期间允许常驻（`C-003`）
- 闲置时停止（`R-003` / `D-002`）—— 因动而动，零闲置能耗

## 三道关卡

设计推导法的审计清单（十一审）中，可自动化的部分已变成三道关卡。它们查的是**三件不同的事**，谁都替代不了谁。

| 关卡 | 命令 | 查什么 |
|---|---|---|
| **① 约束校验** | `node scripts/lumtract-verify.mjs` | 设计值有没有违反钻石约束（123 项：钻石/钢铁 114 + 工程阈值 9） |
| **② 契约测试** | `npx vitest run`（根目录：`npm run test`） | 令牌契约、层级单调、零硬编码、导出一致性 |
| **③ 类型检查** | `npm run build` | 类型是否闭合（**唯一不可替代**） |

### 为什么三道都要

- `verify.mjs` 管不了类型
- `vitest` 用 esbuild transform，**只擦除类型不校验**——所以也管不了类型
- `next build` 每次只报第一个错，但它是唯一能抓到类型错误的

实测案例：一次 `rowKey` 的泛型逆变错误，前两道全绿，只有 build 抓到了。

### 校验规则的硬度分级

**校验规则自己也要有来源标注。** 卷三说「无标注 = 推导无效」——一条没有硬度标注的校验规则，无法被审计、无法被质疑、无法被修正，和被它校验的设计值一样。

123 项分两级，失败时的处理不同：

| 标记 | 硬度 | 项数 | 失败时 |
|---|---|---|---|
| ◆ | 钻石 / 钢铁 | **114** | 阻断（退出码 1） |
| ○ | 工程阈值 | **9** | 仅警告（退出码 0） |

那 9 项工程阈值是**为了达到钻石约束而选的手段**，不是约束本身：

| 项 | 真正的约束 | 为什么它是手段 |
|---|---|---|
| `wave-min-r ≥ 9px` | P-004「100ms 时必须可见」 | 换缓动或容器，7px 也可能够 |
| 遮蔽强度 ΔL\* 下限 8 | P-001（JND ≈ 1） | 8 是工程余量，不是生理阈值 |
| 遮蔽强度 ΔL\* 上限 20 | P-016「装饰性显著性是噪音」 | P-016 没给数，20 是判断 |
| 层级单调 > 1.5 ΔL\* | L-001（只要求单调） | 1.5 是余量，>0 即满足 L-001 |

> 把手段冒充约束，是「陶土说成钻石」的一种变体——
> 而用自动化机制把它固化，等于把这个错误变成不可违抗的律令。

### 固化时机：刻意未做

**本项目没有配置 pre-commit hook，这是刻意的。**

固化的前提是约束已被充分质疑。而当前的真实状态：

| 条件 | 状态 |
|---|---|
| 目的档案经用户访谈验证 | ❌ 所有 `[PURPOSE]` 为临时值 |
| 组件覆盖足够，实例能质疑约束 | ⚠️ 5 个组件，尚未产生质疑 |
| 阈值经过一轮修订 | ❌ 多数为首次设定 |

卷一公理四：**目的是第一推动**。从一个未经证实的起点挤出的链条，不该被自动化机制保护起来。

卷四：**质疑从下往上流**。若此时用 hook 阻断，等于把质疑通道堵死——改一个尚未验证的值要先过校验。

**可以固化的时机**（建议按此顺序）：

1. 目的档案完成真实用户访谈，`[PURPOSE]` 不再是临时值
2. 组件覆盖主要交互场景，实例开始产生质疑
3. 至少一轮阈值修订，且每次修订都记录了依据
4. 此时再加 hook，且**只阻断那 114 项钻石/钢铁**

在此之前，`verify.mjs` 保持「可看、可参考、不阻断陶土」的状态。它输出末尾会明确提示：

```
⚠ 本校验【尚未固化】—— 项目未冻结，阈值仍可质疑。
```

**如何质疑一个阈值**：改 `tokens.ts` 的 `why` 字段，连同依据一并更新。依据先于值——这是这套体系唯一不可妥协的东西。

### 无需 Storybook、无需 vitest 的最快反馈

```bash
cd web-viewer
node scripts/lumtract-verify.mjs
```

零依赖，直接输出 123 项，逐条列出实测值 / 要求 / 约束 ID：

```
  对比度
    ✓ 夜 正文        14.08:1  需 >= 4.5:1  [P-001]
  光敏安全
    ✓ 呼吸频率        0.71Hz  需 <= 3Hz    [P-019]
  热区
    ✓ hit-min         44.00px  需 >= 44px   [P-010]
  层级单调
    ✓ 夜 zebra→hover  3.32 ΔL* 需 > 1.5 ΔL* [L-001]

  全部通过：123 / 123
```

> 这些测试做过变异验证：故意注入违规（热区改 32px、呼吸改 200ms、hover 低于斑马纹），全部被抓到。
> **一个永远通过的测试等于没有测试。**

## 设计哲学：水波与光

Lumtact 的每一个形态都不是被选择的，而是约束空间被诚实挤压后的剩余。

**任何输出的设计值必须携带来源标注**——`[PHYS]` 物理/生理约束、`[ENG]` 工程约定、`[GENE]` 项目基因、`[PURPOSE]` 目的裁决。无标注 = 推导无效。

**方法 vs 皮肤**：本仓库有两种东西——**方法**（Lumtact Method，无色、无风格：卷一 philosophy → 卷二 constraints（含导航分册）→ 卷三 derivation → 卷四 archive）与**皮肤**（显式标注 `[GENE]` 的 demo）。方法论只输出硬边界与推导协议，不承诺任何视觉风格；以下「有机形态」「深海发光」是**皮肤**——一个演示用的项目基因，不是水之波光的本质。任何把特定形态（暗色、圆角、水蓝、微光）提升为"水之波光本质"的表述，都违反哲学附录 v1.1（[philosophy.md](web-viewer/public/docs/philosophy.md)）。

### 皮肤 [GENE] demo · 有机形态

采用自然圆角，但不是因为它"呼应碳基生命"：

```
rounded-xl (12px)
├── [ENG]    4px 网格倍数 → 简化协作与心算
├── [PHYS: P-002] 空间频率 → 分散曲率变化，降低 1x 屏高频锯齿
└── [PURPOSE]    卡片容器 → 软化边界，促进闭合性
```

圆角不是唯一解——抗锯齿渲染、更高像素密度同样是解。它是特定约束集下的诚实解，不是本质。

### 皮肤 [GENE] demo · 深海发光

在深色模式下，交互以辉光聚集代替生硬颜色切换。**关键在"交互时"这三个字**：

```
微光流转
├── [PHYS: R-003] GPU 能耗 → 闲置动画必须停止，禁止常驻流光
├── [PHYS: D-002] LTPO 面板 → 持续动画强制维持高刷新率
└── [PHYS: P-004] 因果下限 → 起手 <100ms 必须可见，尾部才允许缓慢
```

**因动而动，零闲置能耗。** 波纹是事件驱动的：触发时生成，播完自我销毁，节点从 DOM 移除。

昼与夜的反光用不同极性——这不是风格，是动态范围的物理结果：

| 主题 | 基底 | 向上余量 | 向下余量 | 唯一可行极性 |
|---|---|---|---|---|
| 昼 | `#FFFFFF` | 0 级 | 255 级 | 变暗 → 阴影 |
| 夜 | `#1A1A1A` | 229 级 | 26 级 | 变亮 → 微光 |

`[PHYS: D-001]` 白底之上再加白等于没加；近黑之上再压暗只剩 26 级。**昼夜极性由动态范围决定，不是审美偏好。**

### 方法 · 硅基骨架（硬度系统）

底层保持严格的工程约束与高性能数据流。约束分三种硬度，**把陶土说成钻石，是推导中最常见的欺诈**：

| 硬度 | 类型 | 妥协性 |
|---|---|---|
| **钻石** | 碳基生理边界（韦伯阈值、热区 44px、工作记忆 ~4 组块） | ❌ 任何目的下不可妥协 |
| **钢铁** | 硅基物理边界（sRGB 色域、Alpha 合成、GPU 能耗） | ❌ 当前技术下不可妥协 |
| **陶土** | 工程约定与项目基因（4px 网格、品牌色） | ✅ 可随项目上下文调整 |

### 被禁止的推导方式

| 方式 | 错误本质 |
|---|---|
| 类比推导 | 跨通道混淆 |
| 权威推导 | 从表象倒推 |
| 经验推导 | 无法追溯约束 |
| 流行推导 | 流行不是约束 |
| 审美惯性 | 品牌冒充目的 |
| 基因冒充约束 | `[GENE]` 冒充 `[PHYS]` |
| 目的豁免 | 目的不是豁免 |
| 模糊量化 | 约束陈述不精确 |
